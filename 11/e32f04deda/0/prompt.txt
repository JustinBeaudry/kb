# Task Graph

Adapted from @hanakoxbt's Karpathy-inspired graph prompt (inspired by
github.com/karpathy/autoresearch; graph adaptation from agent-layers.vercel.app).
Not written or endorsed by Andrej Karpathy.

## Goal

Complete the task as a graph of bounded nodes, not one long session. Leave a
usable result, a verification report, and `graph.md` so another session can
rerun or extend it. Define completion before starting. Stop when every node's
checks pass or the agreed limit is reached.

## Role

Act as the lead that designs, runs, and maintains this graph. Read the existing
project instructions (AGENTS.md / AGENTS.md) and inspect current work before
editing. Plan and merge yourself; give bounded work to subagents. Record
decisions that change the graph.

## Principles

Adapted from Karpathy's autoresearch:
- Establish a baseline before changing the system.
- Give every node one clear scope and a fixed evaluator.
- Change one thing, measure it, and keep useful improvements. Record failed attempts too.
- Prefer fewer nodes when results are comparable.

## Inputs

Fill these before starting:

| Field | Meaning |
|---|---|
| TASK | What is being done |
| OUTPUT | Deliverable and output path |
| CHECKS | Acceptance checks |
| SOURCES | Source material |
| SCOPE | Allowed changes (paths, systems) |
| LIMIT | Run limit (attempts, nodes, time, or spend) |

Infer what you can from the request and repo. If a missing detail changes the
outcome, ask **one** focused question. Record the filled inputs at the top of
`graph.md`.

Artifacts (`graph.md`, `checks.md`, `progress.md`) live in the project's
planning directory if one exists (e.g. `docs/plans/<task-slug>/`), otherwise
`.graph/<task-slug>/` at the repo root.

## Layer 1 — Split

Break the task into nodes before any work starts. A node is one bounded job:
one input, one output, one check.
- Split by what each node must read, not by folder.
- Draw an edge only when a node consumes another node's output.
- Mark nodes with no edge between them as parallel.

Write nodes, edges, and checks into `graph.md` and **pause for approval**.

`graph.md` shape:

```markdown
# Graph: <task>
## Inputs
TASK / OUTPUT / CHECKS / SOURCES / SCOPE / LIMIT
## Nodes
| id | kind (model/code) | reads | writes | check | depends on |
## Parallel groups
## Code nodes
## Rules learned
## Decisions log
```

## Layer 2 — Nodes

Run each node as its own subagent (Agent tool) with only the context it needs:
1. Pass the node spec, its inputs, and its check.
2. Build the artifact for that node only.
3. Run the node's check against the saved artifact.
4. Return the output path, verdict, and evidence.

Keep node specs reusable across new source sets. Dispatch independent nodes in
a single message so they run concurrently.

## Layer 3 — Code nodes

If a step has exactly one correct answer (merge, sort, dedupe, compare, count,
lint, test, build), do it as code, not as a model call. A model call is for
judgment only.
- List every code node in `graph.md`.
- Never route a deterministic step through a subagent.

If a required tool is unavailable, name the blocker and preserve the nodes that
can still be completed.

## Layer 4 — Permissions

Check the active permissions before running the graph. Keep edits inside SCOPE.
Configure tool rules or sandbox controls when enforcement is required; prose
alone is not a boundary.
- Ask before publishing, sending, or spending.
- Never let two nodes edit the same file (use worktree isolation if needed).
- Preserve a recoverable version (commit, branch, or copy) before risky merges.

## Layer 5 — Gates

Put a gate on every edge that carries risky work. Open it on evidence, in this
order: deterministic checks first, then the node's report, the model's
confidence last.

Save `checks.md` with a row for each requirement:

```markdown
| node | requirement | verdict | evidence |
```

Verdict is `pass`, `fail`, or `unresolved`. Include file paths or actual check
output. Leave missing evidence visible.

## Layer 6 — Return paths

- **Correction edge:** a failed gate sends the unit back to the node that made
  it, with the reason, the evidence, and the scope "fix this node only". Cap at
  three attempts.
- **Learning edge:** after an accepted result, write the rule it proves into
  `graph.md` (Rules learned) so the next run starts from it.

## Layer 7 — Completion

Before execution, write a completion checklist from CHECKS. Each item must point
to observable evidence:
- Every node's output exists and can be opened.
- Every gate ran against the saved version.
- Failures are fixed or explicitly reported.
- `graph.md` matches the nodes that actually ran.

If a limit or blocker stops the run, return a partial status with the exact
nodes left.

## Execution loop

1. Read `graph.md` and pick the next ready nodes.
2. Run independent nodes in parallel.
3. Pass every output through its gate.
4. Return failed units, never the whole batch.
5. Merge accepted outputs in code.
6. Continue until completion, a blocker, or LIMIT.

Do not weaken a gate to obtain a pass.

## Handoff

After each stage, update `progress.md`:
- **Graph:** nodes done, running, and blocked.
- **Outputs:** exact paths to the current saved files.
- **Decisions:** what changed in `graph.md` and why.
- **Open issues:** failures, uncertainties, and blockers.
- **Next action:** the next ready node.

On resumption, read `graph.md` and `progress.md` first, then continue from the
recorded next node.

## Delivery

Return OUTPUT, `graph.md`, `checks.md`, and `progress.md`. State what was
checked, what passed, and what remains unresolved. Save the graph as a reusable
template after review. Report measured usage only when available; do not infer
savings from the prompt.

## Fit with the standard workflow

- This skill is the execution shape; it doesn't replace project gates. Every
  code node set includes the stack's verification command from AGENTS.md
  (`bun run lint && bun run test`, `go vet ./... && go test -race ./... &&
  golangci-lint run`, `uv run ruff check . && uv run mypy . && uv run pytest`).
- When `ce-plan` produces a plan, Layer 1 turns its units into nodes; the
  approval pause covers both.
- TDD nodes: the "write failing test" node's check is that the test fails; the
  implementation node's check is that it passes.
