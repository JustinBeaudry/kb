# O3 usefulness trial: remote memory vs local vault vs none

Linear APP-15. Frozen 2026-11-25 before any solver ran. Local only: the disposable compose fixture (`deploy/compose-smoke.sh`), never Railway or production. All data is synthetic.

## Question

Does remote memory change agent outcomes on tasks that need knowledge from earlier sessions, compared with (A) no memory and (B) the same knowledge in a local KB vault?

This is a small feasibility trial (8 tasks × 3 arms × 1 run = 24 trials). It can show large differences and specific failure modes. It cannot support a statistical or general claim. The designer wrote the tasks with knowledge of both systems. Results, gold and rubric are not tuned after solving.

## Corpus (`corpus.mjs`)

Two synthetic projects, `atlas-api` (8 records) and `birch-pipeline` (7 records). The records cover:

- Superseded decisions. Atlas webhook queue: RabbitMQ (2026-10-02), then NATS JetStream (2026-11-10). Birch dedupe key: `event_id`, then `(source, event_id)`. In remote memory the second decision is published as a new revision of the same target.
- A conflict: two verified Atlas p95 SLO records, 250 ms and 400 ms.
- Owner-verified facts: deploy approver, migration lock timeout, rate limit, key rotation, batch time, escalation owner, retention, schema sign-off, backfill window.
- Unverified candidates: Atlas rate limit 900/min and Birch batch 04:00 UTC. Each was submitted as a candidate and never verified.

**Remote seeding (`seed.mjs`).** This is the real path. A collector uploads and completes the artifact through the HTTP API, a seeding agent submits the candidate (`applicability: {}`), and the host runs `kb-admin verify --preview` then `kb-admin verify`. Candidates are left unverified. Each project gets its own policy (`o3-policy-1`) and its own scoped solver credential (`status:read,retrieval:read,evidence:read`), registered with `kb remote credential-set` under throwaway profiles `o3-atlas` and `o3-birch`.

**Local vault (`prepare.mjs`).** One vault holds both projects, as a personal vault would. Each record is one page with the identical record text, a `status` frontmatter field (`verified`/`candidate`) and a body "Trust" line. A record with two revisions shows the current text plus a "Superseded version" section.

Representation differences are part of what is measured, not controlled away. Remote search hides candidates outside working mode and scopes credentials to one project. The local vault exposes every page to every question.

## Arms

- **none.** `claude -p` with `--tools ""`. The prompt states that no memory is available.
- **local.** `kb` local commands (`list-topics`, `map`, `get-node`, `get`, `recall`) on a fresh copy of the frozen vault. They are reached only through the recording wrapper `tool.mjs`.
- **remote.** `kb remote` (`status`, `orient`, `search`, `fetch`) against the fixture, using the profile for the task's project. They are reached only through the same wrapper, which injects profile and endpoint.

Both memory arms get the same task text, answer format, answering rules and budget. The budget is 16 wrapper calls, 128 KiB of total visible output and 16,000 bytes per call, and the guide counts as a call. Each arm has a short guide of similar length. The arm guides are generated by `prepare.mjs`, and their byte sizes are recorded in the manifest.

## Solver and harness

`claude -p --model haiku --setting-sources "" --strict-mcp-config --output-format json`, one fresh process per trial. Each trial runs in a `/tmp` trial directory, outside the home tree, so no CLAUDE.md, hooks, plugins or MCP servers load. Memory arms run with `--tools Bash --allowedTools "Bash(bun <trial>/tool.mjs:*)"`, so any other command is denied by the permission system and recorded as a denial. The none arm has no tools. Model usage and cost are taken from the harness JSON. The 24 trials run in a fixed hash order, 4 at a time.

Before the freeze there was one harness qualification run: T2 remote, on a discarded probe root. It was used only to fix CLI argument order in `run.mjs` and is not scored. Wrapper probes (`probe-checks.md`) checked the commands before solving.

## Scoring

**Primary outcome: task success.** Every gold fact is stated correctly, no `fail_if` condition holds, and abstention cases abstain without inventing a value.

Reported separately:

1. **Trust handling.** On T2 and T7, did the answer present the unverified candidate as verified or current? This is recorded for every arm where the candidate was exposed.
2. **Leakage.** Did any answer attribute another project's fact to the asked project? Did the trace expose another project's records? The second is mechanical, read from traces.
3. **Superseded handling.** On T1 and T6, was the old decision presented as current?
4. **Evidence exposure.** Did the trace show the gold record text? This is mechanical.
5. **Efficiency.** Wrapper calls, visible bytes (guide included), failed calls, tokens and cost.

**Blinded grading.** An independent assessor agent receives opaque IDs, the question, the answer, trust notes, limitations and gold. It does not receive arm labels, evidence lists or traces. Answer text can still hint at its arm, so blinding is partial. Mechanical checks (exposure, leakage in traces, budgets) come from the traces.

**Invalid trial.** A trial is invalid if it uses a non-wrapper tool successfully, exceeds the budget, or receives gold. An invalid trial is reported, not rescored. A harness failure (no JSON answer) is a failed trial, recorded as such and rerun at most once, with the rerun disclosed.

## Interpretation limits

One model (Haiku), one run per cell, designer-authored tasks, and an agent assessor without human calibration. The corpus is tiny (15 records), so retrieval difficulty is low. The trial tests trust labels, scoping and abstention more than recall at scale.
